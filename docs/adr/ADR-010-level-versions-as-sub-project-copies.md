# ADR-010: Versions of level work packages are copies in their sub-project

## Status

Accepted (2026-11-21). Update 2026-11-22: shared work packages get version copies of their own audience ([#494](https://github.com/netresearch/jira-to-openproject/issues/494)); the decision text and the consequences below are changed accordingly.

## Context

[ADR-009](ADR-009-security-levels-as-private-sub-projects.md) puts each issue with a Jira security level into a private, memberless OpenProject sub-project of its project's OpenProject project and left open how such a work package gets its versions: the fix versions (`versions`), the affected versions (`affects_versions`) and the sprint version (`sprint_epic`). The versions belong to the parent project, which every reader of the parent project sees. Two rolled-back probes on OpenProject 17.9.7 (the comments [7065082968](https://github.com/netresearch/jira-to-openproject/pull/486#issuecomment-7065082968) and [7065329324](https://github.com/netresearch/jira-to-openproject/pull/486#issuecomment-7065329324) on pull request #486) and the source of that version (read in the pilot container under `/app`) show:

- A work package may only use a version shared with its project. `validate_target_versions_are_assignable` and `validate_observed_in_versions_are_assignable` reject any other ID (`app/contracts/work_packages/base_contract.rb:421-444`). `update_versions` prunes the links of a work package to a version that is not shared with its project, through `project.shared_versions` (`app/models/work_package/versions.rb:98-135`). A parent version with sharing `none` is therefore not assignable to a work package of the sub-project; with `descendants` it is.
- A version counts every targeted work package without a visibility check: `issues_count`, `open_issues_count`, `closed_issues_count`, `estimated_hours` and `spent_hours` query `targeted_work_packages` directly (`app/models/version.rb:100-169`). The version overview partial shows these counts and the completion bar (`app/views/versions/_overview.html.erb:56-76`), and the roadmap renders it for every version (`app/views/versions/index.html.erb:60`). In the probe, a parent-only member who could not see the sub-project's work package saw "2 open" on the shared version.
- Native sprint sharing in the Backlogs module is one project setting for all sprints of a project (`no_sharing`, `share_all_projects`, `share_subprojects`, `receive_shared`; `modules/backlogs/app/models/projects/sprint_settings.rb:34-39`), not a setting per version.
- Observed-in links (affected versions) are not counted by `issues_count`, but they are subject to the same assignability rule, so a work package of the sub-project cannot link a parent version either.
- A version owned by the private sub-project, with sharing `none`, is assignable to its work packages, may carry the same name as a version of the parent, counts only its own work packages, and is invisible to a member of the parent only (`Version.visible` false, the parent's roadmap with sub-projects false).
- A version name is unique per project, case-insensitively: `validates :name, presence: true, uniqueness: { scope: [:project_id], case_sensitive: false }` (`app/models/version.rb:48-50`) and the unique index `index_versions_on_project_id_and_LOWER_name` on `(project_id, lower(name))` (`db/structure.sql:13974`). Neither the model nor `app/contracts/versions/base_contract.rb` limits the length of a name, and the column is an unbounded `character varying`.

## Decision

Each level sub-project gets its own copy of every parent version that a selected level work package uses, as a fix version, an affected version or a sprint version.

- **The copy.** It belongs to the sub-project, has sharing `none` and the source version's name, and the description, status, start date and release date that the ordinary path sets: from the Jira release catalogue for fix and affected versions, from the parent's sprint version for a sprint. Only versions a selected level work package uses are copied, not the whole catalogue.
- **Provenance and repeat runs.** The copy carries the same `Jira Version Origin` value as a parent version (Jira base URL, version ID, released and archived flags). `Jira Version Origin` is read per project (`project.versions`) by both the catalogue writer and the observed-version writer, so a copy and its parent version never meet in one lookup. A repeat run adopts the copy by its origin instead of creating a second one. A version of the sub-project with the same name and no origin stops that sub-project's transaction.
- **Mapping.** The copies are recorded in `security_level_version_mapping.json`, keyed by `<sub-project label>:<Jira version ID>` (for example `APP:10000:41`), never in `version_mapping.json`. Sprint copies are recorded under `<sub-project label>:sprint:<Jira sprint ID>`, and their `Jira Version Origin` ID is `sprint:<Jira sprint ID>`, because sprint IDs and version IDs are separate ID spaces. An audience copy (see below) appends `:audience:<token>` to both: `APP:10000:41:audience:<token>` with the origin ID `41:audience:<token>`, and `APP:10000:sprint:42:audience:<token>` with the origin ID `sprint:42:audience:<token>`; its mapping entry adds `audience`, the sorted OpenProject user IDs.
- **Memberless staging.** A copy is created or changed only while the sub-project has no membership row at all, locked users and work package shares included ([ADR-005](ADR-005-project-access-after-memberless-staging.md)), as the categories of the components stage do. An unchanged static copy is still adopted after the access grant. The assignment of a static copy to a work package is not gated: it changes only work packages the sub-project's members can already read. An audience copy is used, also unchanged, only while every membership row is a grant of the level's readers ([ADR-012](ADR-012-late-access-grant-of-level-sub-projects.md)): its counts are shown to everyone a work package that targets it is shared with, so a share left over from earlier readers must stop it.
- **The parent.** The parent's versions and their sharing are never changed. The sub-project transaction checks the Jira origin of the parent and that the sub-project is its private child.
- **Shared work packages get the copies of their audience** (update 2026-11-22; before, they got no target version). On Enterprise a `per_issue` work package is shared with its own extra readers (ADR-009). `Version.visible` includes every version that a work package the user can see targets (`shared_via_work_packages`, `app/models/version.rb:64-80`), and that version's counts and hours include all its targeted work packages, so a share-only reader of a static copy would see the other level issues of that version. So there is one copy per version and audience:
  - The static copy serves every work package that is not shared, as before.
  - The audience of a shared work package is the set of OpenProject user IDs it is shared with, the extra readers of its issue in the readers file (`Audience.shares`). Two work packages share a copy only when that set is equal, so every reader who sees an audience copy through a share can read every work package it counts.
  - **Name.** `<source name> [shared <token>]`, where `<token>` is the first 12 hexadecimal digits of the SHA-256 of the sorted user IDs joined by commas (for example `R1 [shared a9d645f2b0c7]` for users 43 and 44). It depends on the audience alone, so it is the same on every run and in every sub-project, and it differs from the static copy's name, which OpenProject's unique index requires. Two names that collide case-insensitively (a Jira version literally named like an audience copy, or two audiences with one token) stop that sub-project's version copies, before the transaction or through the existing collision check; a sprint issue whose copy ID another audience already holds is refused. Nothing is merged.
  - **Origin.** The `Jira Version Origin` of an audience copy carries the origin ID above and `audience`, the sorted user IDs. A repeat run adopts a copy only when its stored audience equals the row's audience (none for a static copy); otherwise the transaction stops.
  - **Unknown audience.** A shared work package whose audience is not known, because no readers file is configured or none of its extra readers has an OpenProject user, gets no fix version and no sprint version, as before; `versions` and `sprint_epic` count it in `level_versions_withheld`, which is not a failure. It never falls back to the static copy: a later share would show that copy to its readers.
  - Affected versions stay on the static copy: observed-in links neither make a version visible (`shared_via_work_packages` reads `kind: "target"` only) nor count towards it.
- **Selection.** Each component resolves the level work packages through the shared resolver of ADR-009 before any write, reads each Jira project once with the level search, and refuses an issue whose level changed or that the search omits. Unselected and archived issues get nothing.

### Order of work

1. Fix versions and affected versions (`versions`, `affects_versions`).
2. Sprint versions (`sprint_epic`), after pull request #486 (boards) is merged. Native completed sprints (`src/ruby/import_completed_sprints.rb`) stay out of scope: level issues stay out of their manifest.

## Alternatives considered

- **Share the parent version with `descendants`.** Rejected: the counts, hours and completion of the shared version include the level work packages and are shown to every reader of the parent project.
- **No versions on level work packages.** Rejected: the readers of a level see the issue's fix versions, affected versions and sprint in Jira; leaving them out loses data they can see.

## Consequences

### Positive

- A level work package keeps its fix versions, affected versions and sprint, and the version counts of the parent show nothing of it.
- A repeat run, also one after a lost mapping file, adopts the existing copies.

### Negative

- A version or sprint is split across the parent and each sub-project that uses it: the parent's version, its roadmap entry and its sprint board do not show level work packages, and each copy counts only the work packages of its own sub-project.
- A change of a Jira version (renamed, released, new dates) reaches a copy only while its sub-project is memberless; after the access grant a changed copy stops that sub-project's transaction and its issues are refused. Update 2026-11-21: with a readers file, the check accepts the grants of the level's readers ([ADR-012](ADR-012-late-access-grant-of-level-sub-projects.md), decision 9).
- On Enterprise, a level work package shared with extra readers is counted by the copy of its audience, not by the static copy: the static copy's roadmap entry shows only the unshared work packages, and each audience copy is a separate roadmap entry of the sub-project with the token in its name. Without a readers file, or when none of its extra readers has an OpenProject user, the work package has no fix version or sprint version in OpenProject.
- The `Jira Version Origin` of an audience copy names the OpenProject user IDs of its audience, which the adoption check compares. The version API injects version custom fields (`lib/api/v3/versions/version_representer.rb:41`) and serves every version of `Version.visible` (`lib/api/v3/versions/versions_api.rb:51`), so a reader who sees the copy through a share can probably read the user IDs of the other readers of that work package (read from the source, not measured). The token in the name gives no protection either: it is a hash of a small set of IDs.
- An audience copy follows the readers file of the run that assigned it. When a run of `security_level_access` shares a work package with a user that the last `versions` or `sprint_epic` run did not know (the readers file or the user mapping changed in between), that user sees the old audience copy and its counts until `versions` and `sprint_epic` run again, which these components cannot prevent; run them after every access grant that adds readers. A share the readers file no longer names is not revoked by the access stage; it stops the audience copies of that sub-project, and with them that sub-project's version and sprint assignments, until an operator removes it.
- Versions created in OpenProject later are not copied: only versions a selected level work package uses in Jira exist in the sub-project.
