# Operator archive of restricted Jira issues

`j2o-restricted` records who can read each Jira issue that has an issue security level, and keeps every issue that cannot become an ordinary work package of its level in an age-encrypted archive for the operator. `inventory` only reads Jira; it makes no OpenProject request. `admins` reads the archive and OpenProject and changes nothing. Issues with a level stay out of the standard migration unless `security_level_work_packages` is switched on (see [Level work packages](#level-work-packages)). The decisions behind it are in [ADR-009](adr/ADR-009-security-levels-as-private-sub-projects.md).

## What it computes

For each project with an issue security scheme:

1. The levels come from `/rest/api/2/project/{KEY}/issuesecuritylevelscheme`, their grants from the project-config page `/plugins/servlet/project-config/{KEY}/issuesecurity` (Jira 9 has no REST endpoint for them). The page was read with a Jira administrator account; other accounts were not tried. A login or WebSudo page instead of the grant table stops the run.
2. **Static readers** of a level: the members of its group and project-role grants, the project lead and its single users, intersected with the users who have Browse on the project.
3. **Effective readers** of each issue: `/rest/api/2/user/permission/search?permissions=BROWSE&issueKey=…`.
4. Each issue gets one class:
   - `static`: the effective readers equal the static readers.
   - `per_issue`: additional readers, each named by the issue's assignee, reporter or user-field grant.
   - `unexplained`: a reader no grant explains, a static reader missing from the effective readers, or a level with a grant label the command does not know (for example "Current user", or a label in another language). The grants of such a level are not resolved, so the report shows 0 static readers for it. Such issues are archived and the run continues.

The migration account's temporary "Single user" grant (ADR-009, decision 3) is not counted. The account is removed from an issue's effective readers only when the level has a "Single user" grant naming it and no other grant explains it. On a level without such a grant the account stays a reader, and the issue is `unexplained` unless another grant explains the account. Pass its Jira user name with `--migration-account`; the default is `J2O_JIRA_USERNAME`, the configured Jira user. The account must exist in Jira and must own the inventory token: the command compares it with `/rest/api/2/myself` and stops on a mismatch.

## Prerequisites

Jira returns only the issues the token user can read. Before each run:

- The migration account has Browse Projects on every project in scope.
- The temporary "Single user" grant for the migration account is on every security level of every project in scope.
- Without `--project`, the instance total of `level IS NOT EMPTY` checks coverage only for issues visible to the token; an issue the token cannot read is missing from both the total and the scan.

Remove the temporary grants after the final scan.

## Run

The inventory token belongs to the migration account. Set `J2O_ARCHIVE_INVENTORY_TOKEN` through your secret store, and `J2O_ARCHIVE_CA_BUNDLE` when Jira uses a private CA. Run the command in a private directory; archive and report must be plain file names in it and must not exist yet.

```sh
mkdir -m 700 ~/restricted-inventory && cd ~/restricted-inventory
uv run --project /path/to/j2o j2o-comments keygen --identity operator.agekey
uv run --project /path/to/j2o j2o-restricted inventory --jira https://jira.example.org \
  --identity operator.agekey --archive restricted-issues.age --report report.json
```

Without `--project` every project is scanned, and the total of `level IS NOT EMPTY` must equal the issues found. Repeat `--project KEY` to limit the scan.

- `report.json` (mode 600) is the shared run report: counts per project and level (issues, static readers, each class, single-user grants that name the migration account, issues where the account was not counted), the keys of each level's `static` issues (`static_keys`), and the keys of archived issues with their class and the number of extra and missing readers. It holds no reader names.
- `restricted-issues.age` is encrypted to the operator key. It holds every `per_issue` and `unexplained` issue in full (all fields, the complete changelog, the comments visible to the migration account, all worklogs, attachment metadata), with its readers, and each level's grants and static readers. Attachment contents are not included.

Restore the archive on a trusted machine into a new private file:

```sh
uv run --project /path/to/j2o j2o-restricted restore --identity operator.agekey \
  --archive restricted-issues.age --output restricted-issues.json
```

## Edition and administrator report

OpenProject administrators see every work package, so they will see the work packages of every level sub-project. The import does not stop for that (ADR-009, decision 4); `admins` lists them before any level sub-project is created. Run it from the j2o working directory of the migration: the Rails console connection comes from its `config/config.yaml`, and `--user-mapping` names the migration's `var/data/user_mapping.json`. Set `J2O_OPENPROJECT_API_KEY` through your secret store. The report is written to the working directory and must not exist yet; the checkout ignores `restricted-admins*.json`, so keep that name.

```sh
cd /path/to/j2o
uv run j2o-restricted admins --identity ~/restricted-inventory/operator.agekey \
  --archive ~/restricted-inventory/restricted-issues.age --user-mapping var/data/user_mapping.json \
  --openproject https://openproject.example.org --report restricted-admins.json
```

- **Edition.** Rails answers `EnterpriseToken.allows_to?` for `work_package_sharing` and `internal_comments`; `GET /api/v3/configuration` answers `availableFeatures`. The edition is `enterprise` only when both allow `work_package_sharing`; a disagreement is logged and means `community`. A failed or malformed answer, or a Rails console and API URL that report different host names, stops the command; so does a user mapping without a single usable entry. The report keeps both answers (feature names only).
- **Administrators.** Every non-deleted administrator, with its status (`active`, `locked`, `registered`, `invited`). An administrator maps to the Jira users whose user-mapping entry names its OpenProject ID; user names are compared case-insensitively. Per level, `restricted-admins.json` (mode 600) lists the logins of the administrators none of whose Jira users is a static reader of the level. `unmapped_admins` lists administrators without a Jira user; an entry restored from OpenProject (`restored_from_op`) guesses the Jira name from the login and does not count as a mapping. A level with an unsupported grant has no computed readers (`readers_computed: false`) and lists nobody; its issues are archived anyway. The report names administrators only, never Jira readers.

## Level sub-projects

The `security_level_projects` component creates, for each Jira project and level with at least one issue that will go to OpenProject, one private sub-project under the project's OpenProject project (ADR-009, step 3 of the order of work). Static issues count on both editions, `per_issue` issues only when the administrator report says `enterprise`; `unexplained` issues never count. The component reads only the shared `report.json` and the administrator report, never the archive. It is in no profile yet; run it after `projects`:

```yaml
migration:
  security_level_report: /home/me/restricted-inventory/report.json
  security_level_admin_report: /path/to/j2o/restricted-admins.json
```

```sh
uv run j2o migrate --components security_level_projects --no-confirm
```

- **Precondition.** Both files must exist, have their format and name the same `archive_sha256`; otherwise the component stops before any OpenProject request. The content of the administrator report never stops it; only its `edition` is used. That edition is the one detected when `admins` ran: run `admins` again after a licence change.
- **Identifier and name.** The identifier is the Jira project's identifier (lower case, `-` for every other character, `p-` before a leading digit) followed by `_level_` and the level ID, for example `app_level_10000`. A key-derived identifier never contains `_`, so it cannot equal one; an identifier longer than 100 characters is refused. The name is the parent's current OpenProject name, read from OpenProject in the same request that looks for the sub-project, with the level name in parentheses, for example `App (Management)`. An identifier or name that belongs to an entry of the project mapping is refused.
- **Parent.** The parent is the OpenProject project of the Jira project in `project_mapping.json`. When that file has no entry with an OpenProject ID for one of the Jira projects, the component reads the project entries of the J2O provenance registry once, as `ProjectMigration.restore_mapping_from_openproject()` does, without rewriting `project_mapping.json`; restored names count as known names. A level whose parent is found in neither, or whose parent no longer exists in OpenProject, is refused.
- **Properties.** The sub-project is created with `public: false`, its parent's types (a variant the parent owns falls back to the type's base variant) and the modules `work_package_tracking` and `wiki`, through `Project.new` rather than `Projects::CreateService`, which would add the creating user as a member. No member is added; OpenProject 17.9.7 copies no memberships from a parent project. It carries no J2O Origin fields, so lookups by Jira project key keep finding only the parent.
- **Mapping.** `security_level_project_mapping.json` holds one entry per `<Jira key>:<level ID>` with the OpenProject project ID and identifier. `project_mapping.json` stays one project per Jira project.
- **Repeat runs.** An existing project with the identifier is accepted only when it is private, has no membership row (locked users and work package shares included) and has the expected parent. Otherwise that level is refused and reported, and the project is not changed. Work packages go into the sub-projects only with the level switch on (see [Level work packages](#level-work-packages)).

## Level work packages

With `migration.security_level_work_packages: true`, `work_packages_skeleton` and `work_packages_content` also migrate the issues of every level that has a sub-project (ADR-009, step 4 of the order of work), `attachments`, `attachment_provenance` and `attachment_recovery` handle their attachments, `simpletasks` and `components` their tasks and categories, `work_package_field_history` and `time_entries` their field history and time entries, `versions` and `affects_versions` their fix and affected versions, `sprint_epic` their sprint versions, `relations` and `inline_refs` their relations and inline attachment references, and `agile_boards`, `native_boards` and `sprint_epic` keep them out of the boards and sprints of the parent (step 5). The switch is off by default, and only the boolean `true` turns it on. Leave it off until the other dependent components (watchers) and the late access grant are in place: until then a level work package has no watchers, and no member can read it.

```yaml
migration:
  security_level_report: /home/me/restricted-inventory/report.json
  security_level_admin_report: /path/to/j2o/restricted-admins.json
  security_level_work_packages: true
```

- **Selection.** Per Jira project, one search `project = KEY AND level IS NOT EMPTY`, split by the level ID each result carries (`fields.security.id`); a search per level fails with HTTP 400 for a level of which the migration account sees no issue. The report lists the keys of each level's `static` issues and of its archived issues. `static` issues go on both editions, `per_issue` issues only when the administrator report says `enterprise`, `unexplained` issues never.
- **Fail closed.** A search result without a level ID is refused. A level is refused as a whole when the search does not return exactly the issue keys the report lists for it (an issue created, deleted or moved since the inventory refuses its level; run the inventory again during the cutover freeze), when an archived issue has another level in the search than in the report, or when its sub-project entry names another project, level or identifier. An issue of a level without a sub-project entry is created nowhere (`unmapped`). Before the first work package goes into a sub-project, the skeleton reads it again: it must exist with the mapped ID, be private, have no membership row and have the mapped parent. The skeleton also reads the work packages the sub-project already holds, by their `J2O Origin Key`: a work package of a selected issue is recorded in the mapping instead of being created again (`adopted`), so a lost mapping file or a lost batch answer never yields a second work package. A sub-project that holds a work package without exactly one origin key, two work packages for one issue, or a work package of an issue not selected for it, is refused. An issue that already has a work package in `work_package_mapping.json`, or one in another sub-project, is refused. With the switch on, a missing or mismatched report stops the component before any write. Refusals make the component unsuccessful; `details.security_level` counts them.
- **Mapping.** Level work packages are recorded in `security_level_work_package_mapping.json`, never in `work_package_mapping.json`, so the components that read the work-package mapping keep leaving them alone until they are adapted. An entry carries `jira_key`, `openproject_id` and `project_key` as usual, plus the sub-project's `openproject_project_id`, `security_level_id`, `security_level_project` (`<Jira key>:<level ID>`) and `security_class`.
- **Content.** `work_packages_content` repeats the selection on a search that reads only the level, then reads, per sub-project, the work packages it holds right now by `J2O Origin Key`, and writes description and custom fields of a selected issue only into the work package its sub-project holds for it. A mapping entry, when there is one, must name that work package, level and sub-project; a missing entry is recovered from the live read. A selected issue without a work package in its sub-project (moved away or never created), an entry that names another work package, and every issue of a sub-project that cannot be read are refused and count as failures. It adds no watchers. Comments take the same path as on every issue (ADR-007): only comments an anonymous request can read become journals, so a comment of a level issue becomes a journal only if Jira shows it to anonymous users, which a level normally prevents; the others stay in Jira. Jira keys in text are linked only to work packages of `work_package_mapping.json`; a reference to a level issue stays a plain key.
- **Attachments.** An attachment inherits the visibility of its work package, so it goes only into the level work package. `attachments`, `attachment_provenance` and `attachment_recovery` each repeat the selection on a search that reads only the level, read each sub-project once by `J2O Origin Key` and resolve a selected issue to the work package its sub-project holds right now; a mapping entry, when there is one, must name that work package, level and sub-project, and a missing entry is recovered from the read without being written back. The Jira project key prefix and `project_mapping.json` are not used for it. When `attachments` (also on behalf of `attachment_recovery`) reads the attachments, it reads the level again; an issue whose level changed since the selection gets nothing and counts as a failure (`extract_level_changed`). A selected issue without a work package in its sub-project, an entry that names another work package, every issue of a sub-project that cannot be read, and an entry of an issue the selection does not keep are refused; refusals count as failures and appear in `details.security_level`. Unselected issues (`per_issue` on Community, `unexplained`, levels without a sub-project) get nothing: their attachments are neither downloaded nor uploaded. An issue of a level search or of the archive that also has an entry in `work_package_mapping.json` gets nothing on either side and is refused. `attachment_mapping.json` records level attachments under their Jira key like every other, so that `work_packages_content` can link inline images of the same issue. No component writes level work packages into `work_package_mapping.json`. With the switch off the three components issue the same requests as before.
- **Tasks and categories.** `simpletasks` and `components` resolve the level work packages like the attachment components, before any write: a selected issue goes only into the work package its sub-project holds for it now, and the refusals above apply. Each reads the issue again with the level search and refuses an issue whose level changed since the selection, or that the search no longer returns; `simpletasks` also checks the level on its per-issue re-read. The sub-project carries no Jira origin of its own, so the Rails transaction checks the origin of the parent and that the parent is the sub-project's parent. Tasks and their **Jira tasklist origins** register go into the sub-project. OpenProject categories belong to one project ([Work package categories](https://www.openproject.org/docs/user-guide/projects/project-settings/work-packages/#work-package-categories): "specific to a project"), so the sub-project gets its own categories and its own **Jira component membership origins** register; a parent category is never assigned to a level work package. Both stop a change when the sub-project has any membership row, locked users and shares included, so they stage only while it is memberless. The `category` mapping records the sub-project's categories under the sub-project's ID. Issues of a level search or of the archive lose their ordinary targets in both components.
- **Field history and time entries.** `work_package_field_history` and `time_entries` resolve the level work packages the same way, before any write. The field history reads the changelog through the level search, refuses an issue whose level changed or that the search omits, and writes the same audience-safe selection as for every issue (ADR-004) into the level work package: its readers are the level's readers, and Jira shows the History tab to everyone who can browse the issue. A change of the security level itself is kept, also one that names another level; readers of the level work package see the same entry in Jira (ADR-004, update of 2026-11-21; the History-tab premise is not measured for level issues). An ordinary work package of an issue that now has a level still gets its value removed. `time_entries` reads a selected issue's work logs only while the issue still has the selected level (`issue/{key}?fields=project,security` before the work log pages); otherwise it gets nothing and counts as refused. A work log with its own visibility stays refused. The expected project of each time entry is the sub-project; OpenProject takes the entry's project from the work package, and the writer refuses a mismatch. Tempo entries are kept only for work logs read this way, as for every issue.
- **Field components.** `customfields_generic`, `priorities`, `story_points`, `estimates` and `wp_metadata_backfill` resolve the level work packages the same way, before any write, refuse an ordinary entry of a level issue on both sides (so no value of an issue that now has a level reaches its ordinary work package in the parent) and read the selected level issues once per Jira project through the level search (fields `*all`), never through the ordinary batch read; an issue whose level changed or that the search omits is refused and gets nothing. Each writes the values of a selected issue into the work package its sub-project holds for it; a custom field with a level value is enabled in the sub-project only. `wp_metadata_backfill` writes only the provenance fields of a level work package, never its assignee (the skeleton sets the assignee from the same Jira field). The level entries exist only for the run; `work_package_mapping.json` never holds them. `labels`, `votes`, `native_tags`, `remote_links`, `resolution` and `security_levels` write nothing with a work-package mapping keyed by Jira issue ID, which is how the skeleton stores it ([#498](https://github.com/netresearch/jira-to-openproject/issues/498)), so they write nothing for level work packages either; `native_tags` would create project-wide tags, but OpenProject 17.9.7 has no `Tag` model and its work packages have neither `tags` nor `tag_list`. A custom field that only level issues use is created as a global field definition.
- **Boards and sprints.** `agile_boards`, `native_boards` and `sprint_epic` resolve the level work packages the same way, before any write, and report the refusals above. No issue of a level search or of the archive goes on a board query of the parent or into a snapshot of the native board archive, also when it has an entry in `work_package_mapping.json`; such an entry is refused. A level sub-project gets no board: the queries of `agile_boards` are private to the migration user and the board archive is a memberless project, so no reader of a level would see one, and a Jira board mixes the cards of all levels. `sprint_epic` reads level issues only through the level search (with the sprint field and `fixVersions`) and writes nothing for them but the sprint version: a selected level work package without fix versions gets the sub-project's copy of the parent's sprint version (see **Sprints** below), but no **Sprint** field and no parent link, also when the origin scan of the parent finds a work package of one; an ordinary work package whose epic or parent is a level issue gets no link to it (`unresolved_epics`, as for any parent that is not migrated). With the switch off, a native board with a card of an issue that has a level still fails, as before. The [native sprint import](native-completed-sprints.md) resolves each manifest issue to a work package of the parent and stops on a level issue, so its manifest leaves them out.
- **Versions.** A version of the parent project cannot be assigned to a work package of the sub-project unless the parent shares it, and a shared version shows the counts and hours of every work package that targets it to every reader of the parent ([ADR-010](adr/ADR-010-level-versions-as-sub-project-copies.md)). So `versions` and `affects_versions` give each sub-project its own copy of every Jira version a selected level issue uses as a fix version or an affected version: sharing `none`, the same name, and the description, status and dates from the Jira release catalogue. The copy carries the same `Jira Version Origin` value as the parent version; a repeat run adopts it by that origin instead of creating another one, and a version of the sub-project with the same name but no origin stops that sub-project. The copies are recorded in `security_level_version_mapping.json` under `<Jira key>:<level ID>:<Jira version ID>`, never in `version_mapping.json`. On Enterprise, a `per_issue` work package (shared with its extra readers) gets no fix version: a share-only reader would otherwise see the counts of the copy, which include the other level issues; `details.level_versions_withheld` counts these, and they are no failure. Affected versions still link it. A copy is created or changed only while the sub-project has no membership row, locked users and shares included; otherwise its issues are refused. Both components resolve the level work packages before any write, read each Jira project once with the level search (fields `project,security,fixVersions` or `project,security,versions`) and refuse an issue whose level changed or that the search omits; `affects_versions` reads the release catalogue of a project only when one of its level issues has an affected version. The parent's versions and their sharing are not changed, so the parent's version counts and roadmap do not show level work packages, and each copy counts only its own sub-project.
- **Relations.** OpenProject 17.9.7 shows a relation whose other end the user cannot see as a placeholder row in the Relations tab, with its type and, for follows and precedes, that end's dates, and counts it in the tab (`app/components/work_package_relations_tab/relations_mediator.rb:122-131`, `relation_component.html.erb:70-109`); only the API leaves it out (`app/models/relations/scopes/visible.rb:49-57`). A rolled-back probe on the pilot confirmed this for a member of the parent only: the API listed no relation, the tab showed one placeholder of type follows with the dates of the level work package and no subject or ID. So `relations` writes a relation between two level work packages only when both lie in the same sub-project and neither is a `per_issue` work package (on Enterprise it is shared with its extra readers, who would see the other end as a placeholder). Every other link of a level issue, and every link of an ordinary issue to a level issue, is withheld and counted in `details.level_relations_withheld`; withheld links are no failure. The links of the selected issues are read with the level search (fields `project,security,issuelinks`), never from `jira_issues_cache.json`; an issue whose level changed or that the search omits is refused and gets no relation, and both ends must be in the result of that search. An ordinary entry of a level issue is refused on both sides, also when the cached snapshot carries its links. `j2o-references` refuses a mapping file with level entries (`security_level_project`), so a deferred reference never reaches a level work package.
- **Inline references.** `inline_refs` rewrites the attachment links of each level work package like those of any other, in the work package its sub-project holds for the issue; it reads Jira only for the level selection (the light search of every Jira project, so it needs Jira access with the switch on), the rewrite itself reads OpenProject only, and an ordinary entry of a level issue is refused. Jira keys in text are converted by `work_packages_content`: ordinary text never links a level issue (the key stays plain), and the text of a level work package links the keys of ordinary work packages. For a reader who cannot see such a target, OpenProject renders the link as a bare `#id` without subject (`lib/open_project/text_formatting/matchers/link_handlers/work_packages.rb:124-150`). A key of another level issue, also of the same sub-project, stays plain.
- **Sprints.** Native sprint sharing is one setting per project, not per sprint (`modules/backlogs/app/models/projects/sprint_settings.rb:34-39`), so a level work package gets its own copy of the parent's sprint version as well (ADR-010). `sprint_epic` picks the sprint as on the ordinary path: the first sprint, by name, whose version in the `sprint` mapping belongs to the parent project, and only when the issue has no fix version (the fix versions own the target version). The copy takes name, description, status and dates from the parent's sprint version, has sharing `none`, carries a `Jira Version Origin` with the ID `sprint:<Jira sprint ID>` and the parent version's ID, and is recorded in `security_level_version_mapping.json` under `<Jira key>:<level ID>:sprint:<Jira sprint ID>`. The same staging rule applies as for fix versions. A level issue whose sprint has no mapped version of the parent, or whose sprint has no ID, is refused. On Enterprise, a `per_issue` work package gets no sprint version either, for the same reason as the fix versions (`level_versions_withheld`). The parent's sprint, its board and its counts do not show level work packages; each copy counts only its own sub-project.
- **Watchers.** A level work package gets no watchers yet. Only a reader of the level may watch it, and the importer has no readers: `report.json` carries the number of static readers per level (`static_readers`) and of extra readers per archived issue, never their names, and the reader identities (each level's static readers, each `per_issue` issue's extra readers) are only in the age-encrypted archive, which the importer does not read. `watchers` resolves the level work packages before any write, reads no watcher of a level issue (also not from `jira_issues_cache.json`), counts the level work packages it leaves without watchers in `details.level_watchers_withheld`, and refuses an ordinary entry of a level issue; refusals count as failures in `details.security_level`. `work_packages_content` collects no watchers for level work packages either. The late access grant (step 6 of the order of work) needs the same reader identities.
- **Limits.** `J2O_MAX_ISSUES` does not limit the level search, because the selection has to see every issue of a level. An issue created, deleted or moved since the inventory refuses its level, so repeat the inventory at cutover. With the switch on, an issue that loses its level after its work package was created is not created again in the parent project, and its work package stays in the sub-project; with the switch off it would get a second work package in the parent project.

## Repeat runs and known limits

Grants and memberships can change until cutover. Repeat the inventory at cutover, in a new directory or with new file names: archive and report are never overwritten. A failed run is repeated the same way, in a new directory, even when it already wrote the archive.

- An issue whose assignee, reporter, reader field or grants change during the scan can be misclassified, because its fields are read before its readers. Run the final inventory during the cutover freeze.
- The archive holds the comments visible to the migration account. With the temporary grant and the account's admin roles this is expected to be all comments; it has not been measured.
